# Linux and Steam Deck

The loader, runtime, launcher and video core run natively on Linux x86-64 as on Windows: the game's own code executes
on the host CPU, the PS4 system libraries are replaced by `src/runtime_*.c`, and the renderer is the same Vulkan video
core. The release is one x86_64 AppImage, which is also the Steam Deck download. This page lists what differs from
Windows, how the AppImage is built, and what has and has not been verified.

## Platform parity

Generated by `python scripts/feature_parity.py --platforms` and checked by `tests/feature_parity_tests.py` against the
sources (released renderer, overlay option, Frame rate modes, which presenters repeat frames, Gamescope detection, data
folders, SIGPIPE) and against the suites both test gates run. SUPPORTED: the same code on both platforms. EQUIVALENT:
the same result through the platform's own mechanism. The Steam Deck column is what the AppImage is expected to do
under SteamOS; it has not been tested on Steam Deck hardware.

Only one feature is missing on Linux, for want of a Windows API: Allow overlay programs (Linux overlays are Vulkan layers
or `LD_PRELOAD` libraries that attach to the game process as it is). Alienation PC v0.1.0 requires Vulkan on Linux and
the Steam Deck: there is no renderer setting and no fallback renderer. Online play uses the same lobby protocol, online
version, room model (Matching2, a full mesh of up to four peers), P2P transport and relay on both platforms, so Windows
and Linux players of the same build play together.

## What differs from Windows

| Area | Linux |
| --- | --- |
| Toolchain | Clang 20, non-PIE (`-no-pie`): the host heap handed to the guest (thread handles, TLS) must stay below 1 TiB. |
| Guest memory | One sparse `memfd` backs direct and flexible memory; guest addresses are reserved below 1 TiB with `MAP_FIXED_NOREPLACE`. |
| Faults | A `SIGSEGV` handler (GPU page tracking, speculative reads) in `src/loader.c`. |
| Closed sockets | `SIGPIPE` is ignored before the launcher starts: a lobby or router that closes its connection fails the write instead of ending the program (`tests/sigpipe_tests.c`). |
| File names | The PS4 file system ignores case, Linux does not: `src/runtime_file.c` matches a missing path component without case. |
| Hashes and ciphers | OpenSSL's libcrypto (`launcher/crypto_openssl.cpp`) instead of Windows CNG; the boot image is byte-identical. |
| Lobby connection | `src/net/websocket_posix.cpp` with the bundled OpenSSL; certificates from the distribution's CA bundle. |
| Videos | FFmpeg built by `tools/build-ffmpeg.sh` from `gpu/ffmpeg.txt`, the same LGPL configuration as on Windows. |
| Logs | `src/runtime_log_posix.c`: `logs/alienation_NNN.log`, echoed to the console. |
| Data folder | Beside the AppImage file (`$APPIMAGE`); `ALN_PORTABLE_DIR` overrides; when that folder is read-only, `$XDG_DATA_HOME/AlienationPC` (`~/.local/share/AlienationPC`). Never inside the AppImage, whose mount is read-only. Game, saves, settings, logs and shader cache all live there, so they survive updates. |
| File chooser | `zenity` or `kdialog` when installed, otherwise the launcher's own chooser (mouse, keyboard and controller). `ALN_FILE_CHOOSER=builtin` or `native` forces one. |
| Open folder | `xdg-open`. |
| Show the launcher | `--launcher` (or the desktop entry's **Show launcher** action). Holding Shift at start works only on an X11 desktop: Wayland and Gamescope do not report keys to a program without focus. |
| Windowing | SDL3 on X11 or Wayland, Vulkan surface; F11, resize and VSync are the same code. |

## Frame rate, Gamescope and the Steam Deck

The Frame rate setting is presentation only on both platforms: the game keeps running at its original 59.94/60 frames a
second, so gameplay speed, online play and local co-op never change. 30 shows every second frame; 90 to 240 and
Unlimited show the latest game frame again between new ones (repeated frames, no interpolation). The Vulkan
presenter repeats frames, on Linux as on Windows.

Under Gamescope (Steam Deck Gaming Mode, detected by `GAMESCOPE_WAYLAND_DISPLAY`) the swapchain asks for the surface's
minimum image count and a guest flip waits until the presenter has taken the previous frame, which keeps a Steam frame
limit from queueing frames (`tests/present_tests.cpp`). Gamescope paces presentation itself, so VSync Off and Frame rate
settings above the display's refresh may not show there. Gamescope shows the game full screen; display mode and
monitor selection have no effect in Gaming Mode.

## Steam Deck

1. In Desktop Mode, download `AlienationPC-v<version>-x86_64.AppImage` into a folder of its own (for example
   `~/Games/Alienation`); the game, saves and logs will be created beside it.
2. Make it executable: right-click, **Properties**, **Permissions**, **Is executable** (or `chmod +x` in a terminal).
3. Start it once in Desktop Mode, press **Install game...** and select your own Alienation `.pkg` (the launcher's own
   file chooser lists the Downloads folder, the home folder and mounted drives such as the SD card).
4. In Steam, **Games**, **Add a Non-Steam Game to My Library**, browse to the AppImage and add it.
5. In Gaming Mode, start it from the library. To open the launcher there (settings, online, installing), add
   `--launcher` to the shortcut's **Launch Options** in its **Properties**, then remove it again to start straight into
   the game. In game, L3 + R3 opens the Options menu.

The Steam Deck support is what the Linux build is designed to do there; real Steam Deck hardware, Gaming Mode online
play and controller behaviour still have to be tested by hand.

## AppImage

`usr/bin/alienation` carries `DT_RPATH=$ORIGIN/../lib` and each bundled library `DT_RPATH=$ORIGIN` (never
`DT_RUNPATH`, which a host `LD_LIBRARY_PATH` such as Steam's runtime would override), so the bundled libraries (SDL3,
FreeType, libpng, OpenSSL, fmt, Zydis, xxHash, FFmpeg) are always the ones loaded. No `LD_LIBRARY_PATH` is set, so
programs the launcher starts (`zenity`, `xdg-open`, `curl`) are not affected. glibc, the Vulkan loader and drivers, X11/Wayland and the audio
libraries come from the system; the Vulkan loader must support Vulkan 1.3. `libstdc++` and `libgcc_s` are carried in
`usr/lib/compat` and used by `AppRun` only when the system's are older than the build needs.

The AppImage needs glibc 2.31 (Ubuntu 20.04) or newer. `tools/package-linux.sh` refuses to package on a system with a
newer glibc, reads the version needs of every ELF file in the AppDir (found by content) and stops if any needs more
than 2.31 or if the package carries a part of glibc. It also stops on game data, user data, logs, debug files, local
paths, `DEBUG_SAULO`, a GPL FFmpeg, an invalid desktop entry or AppStream file, or an unresolved library.

### FUSE and the AppImage runtime

An AppImage mounts itself with FUSE before `AppRun` runs, and nothing changes where that works. Where the mount cannot
be made (no usable `fusermount`, a restricted environment), the project's runtime unpacks the AppImage into a private
folder under `$TMPDIR` (or `/tmp`), runs `AppRun` from there with the same arguments, passes termination signals on and
removes the folder afterwards. `--appimage-extract-and-run` (or `APPIMAGE_EXTRACT_AND_RUN=1`) forces that mode, and
`--appimage-extract` unpacks it. `$APPIMAGE` keeps naming the original file, so the data folder rules above hold in
every mode.

The released upstream runtime stops when FUSE fails, so the project builds its own:

- `patches/appimage-runtime/baseline.env` pins the upstream [AppImage/type2-runtime](https://github.com/AppImage/type2-runtime)
  repository, tag `20251108`, commit `dd6cebe`, the Alpine root file system the build runs in (version and SHA-256) and
  the SHA-256 of the reviewed result.
- `patches/appimage-runtime/0001-extract-and-run-when-fuse-fails.patch` adds the fallback, gives each run its own
  extraction folder and fixes the cleanup.
- `tools/build-appimage-runtime.sh` fetches the pinned commit, applies the patch, builds it in the pinned Alpine chroot
  and refuses a result that does not match the pinned SHA-256; it rebuilds only when the pins, the patches or the script
  change (a fingerprint stamp). `--check FILE` verifies a runtime or a finished AppImage, and `tools/package-linux.sh`
  checks the written AppImage with it.
- The reviewed runtime has SHA-256 `9e458da0…4ab8`, the same file Dragon's Crown Pro, Odin Sphere and 13 Sentinels pin.
  The chroot build resolves Alpine packages when it runs, so it stops reproducing that file once they move on (a newer
  `zlib` alone gives another binary of the same size); a rebuilt result is therefore never a reason to change the pin.
  `ALN_APPIMAGE_RUNTIME=FILE` makes the build script use an existing copy, and only if its SHA-256 is the pinned one.
  `tools/package-release.ps1` keeps that copy in the ignored `cache/appimage-runtime/runtime-x86_64`, copies it from a
  WSL packaging cache (`tools/import-appimage-runtime.sh`) when missing and deletes any file with another hash.
  `tools/package-linux.sh` then checks that the bytes in front of the written AppImage's file system equal the pinned
  runtime, apart from the sections `appimagetool` fills (`.digest_md5`, `.upd_info`, `.sha256_sig`, `.sig_key`).

### Updates

The built-in updater is the only update mechanism; the AppImage carries no AppImage update information and no
`.zsync` file. It reads the latest release of `saulob/alienation-pc`, downloads `AlienationPC-v<version>-x86_64.AppImage`
and its `.sha256` from that repository's release assets only (every redirect is checked), verifies the SHA-256, writes
the new file beside the running one, keeps a hard-linked backup, replaces the original file (`$APPIMAGE`) in one rename
and starts that same file with `--launcher`. A replacement that cannot start puts the previous AppImage back. Nothing
inside the read-only mount is touched, and the running copy keeps reading its old file until it exits
(`tests/update_network_tests.cpp`). Before the first release is published, the release address answers 404; the
updater reports that as "no release published yet", not as an error.

### Submitting to appimage.github.io

The AppImage carries what the catalog reads: the desktop entry `io.github.saulob.alienation_pc.desktop` (with a
**Show launcher** action), the icon, and the AppStream file
`usr/share/metainfo/io.github.saulob.alienation_pc.appdata.xml` with the version and date of the release. The
catalog's entry points at the published release asset:

```
https://github.com/saulob/alienation-pc/releases/download/v<version>/AlienationPC-v<version>-x86_64.AppImage
```

The submission is a pull request to [AppImage/appimage.github.io](https://github.com/AppImage/appimage.github.io)
adding `data/Alienation_PC` with that URL as its only line, made by hand after the release is public.

## Building

Releases are built on Ubuntu 20.04. `packaging/linux/ci-deps.sh` prepares a clean 20.04 system as root: Clang 20,
the GCC 14 C++ library, CMake, nasm and the distribution's development packages, plus what 20.04 lacks or ships too old,
built into `/usr/local` from pinned, checked sources (Vulkan headers, VMA, glslang, Boost headers, fmt, Zydis, xxHash,
robin-map, OpenSSL 3.5, SDL3 and FFmpeg).

| Command | Result |
| --- | --- |
| `tools/build.sh` | fetches `gpu/deps.txt`, builds `build/cmake/linux/bin/alienation` (RelWithDebInfo, like Windows) |
| `tools/build.sh --test` | the Linux test gate: every portable suite, a check that every test target is run, the Python suites (`.venv` with Python 3.10+), the lobby tests and the online HLE test on a loopback lobby (Node.js 22.13+), `git diff --check` in a checkout, and the platform parity summary; non-zero on any failure or missing dependency |
| `tools/package-linux.sh` | `dist/AlienationPC-v<version>-x86_64.AppImage` and `.sha256`; debug symbols in `dist/<name>-symbols/`, not packaged |
| `packaging/linux/smoke-test.sh FILE` | starts the AppImage's launcher on a virtual display three ways (extracted, `--appimage-extract-and-run`, the file itself) and checks it stays open and keeps its data beside the file |
| `tools\package-release.ps1` (Windows) | the Windows ZIP and the AppImage in one run; the AppImage is built in the WSL2 distribution `AlnFocalBuild` (`-WslDistro` picks another Ubuntu 20.04 one) |

To make the release environment in WSL2, import the Ubuntu 20.04.5 base image
(`ubuntu-base-20.04.5-base-amd64.tar.gz` from https://cdimage.ubuntu.com/ubuntu-base/releases/20.04/release/, SHA-256
`60e216b60947653dc8989be3821380268315b99b2959c29882781541bfe5a426`, listed in that folder's signed `SHA256SUMS`) and
prepare it once from the repository folder:

```powershell
wsl --import AlnFocalBuild <folder> ubuntu-base-20.04.5-base-amd64.tar.gz --version 2
wsl -d AlnFocalBuild -u root -- bash packaging/linux/ci-deps.sh
```

The build never reads another project's sources or build outputs.
